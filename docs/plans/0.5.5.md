## Required contents

Tamlinux 0.5.5 must deliver all three outcomes together:

1. Matching libraries let the packaged `tam` and `tam-monitor` run, and let
   Fred continue developing both commands without reconstructing dependencies
   by hand after a deployment.
2. A compiled C `tam-monitor`, backed by our own library, selects which
   monitors remain lit on a real Linux text console. With three connected
   displays, any one can remain usable while the other two stay blank during
   normal terminal work.
3. The exact `tam` command and corpus that Fred selects after finishing his
   current development. These versions are deliberately **pending Fred**.

The [monitor implementation plan](../../../tamlinux/docs/plans/console-monitor-control.md)
owns native API design, feasibility, recovery and physical acceptance. This
file owns component selection, packaging, developer access and release gates.
Tamlinux commands may be compiled programs; package discovery must not assume
that every `commands/<name>/` entry contains an executable shell script.

## What 0.5.4 establishes, and what it missed

The recorded [0.5.4 delivery](../../deliveries/tamlinux-0.5.4.json) selects
`tam` command 0.43.2, corpus 0.43.0 and libtam 0.4.0 at
`a051ebf457e41a27d47d273bdab291430cabd7ad`. Its package recipe links that
library into `tam`, and the installed-component check compares the embedded
version. Thus the available assembly evidence does not show that the packaged
`tam` itself used an older libtam.

Fred's subsequent `make dev` failure identifies a distinct unresolved
development-environment problem. The developer module currently selects basic
C tools, but does not expose the assembly's libtam headers/archive/pkg-config
metadata. Runtime build dependencies do not automatically become the user's
development dependencies. Trace what Fred's shell actually resolves before
classifying an old or missing library; preserve this distinction in the fix.

0.5.5 must close both paths. Updating a version string, adding a build input,
or compiling a test consumer inside a Nix derivation cannot by itself prove
that a fresh text-login shell can build the next `tam` version.

## Development packages are part of delivery

Extend the reusable developer module with explicitly selected assembly
development dependencies, supplied from the same component set as runtime
packages. Fred's developer profile must expose:

- Core and display headers, static archives and corresponding `.pc` files.
- A compiler, linker, make and pkg-config, plus required headers/libraries
  for the selected `tam` and monitor builds, including terminal/zlib support
  where actually required. Honour native ownership of standard build tools.
- A normal pkg-config search path that resolves these exact packages from
  a fresh text login without a manually installed libtam under `/usr/local`
  or a leftover development prefix. Support explicit `LIBTAM_PREFIX` too.

Separate minimal runtime and development selections so constrained machines
need not load or install a full toolchain merely to run a monitor command.
Fred's development profile receives the build dependencies; the minimal
runtime profile receives only runtime necessities. Installed files consume
disk; they are not all loaded into memory. Measure disk closure and loaded
memory separately. Do not change which package manager owns existing tools
merely to implement this plan.

Use core-only/display-only build and install targets so desktop portal
development dependencies stay optional. Preserve the separate portal archive
for tools that actually use it. Make minimum versions and header/archive
changes trigger correct client rebuilds. A copied old static archive must
not remain eligible simply because a version label changed.

Treat `~/.local/dev` as an explicit temporary override during development,
with build identity visible. After the package delivering that work is
activated, remove only superseded overrides through their uninstall targets,
dependents first, and recheck resolution in a fresh shell. Do not remove an
override Fred is still developing. Final developer acceptance must pass with
no accidental override masking the assembly.

## Packaging work

All Tamlinux 0.x releases are developmental. Keep symbol tables and debug
information in our built executables and library objects, including the final
installed packages, for debugging and core-dump analysis. Add compiler debug
information alongside the chosen optimization settings, disable automatic
stripping/debug removal in build, install and package fixups, and verify
symbols, debug sections and build identity after those fixups. Apply this
to affected Tamlinux-built components, including static library objects whose
debug information must reach the consuming executable. Defer stripping and
stripped-size budgets until after Tamlinux 1.0 is released; measure actual
unstripped disk size and runtime memory separately during 0.x development.

1. Add the library build targets and development metadata in `libtam`; keep
   source files modular so `tam` does not link the display backend or portal.
   Record source/API versions and rebuild every affected static consumer.
2. Add C build/check/install targets under product `commands/tam-monitor/`.
   Adapt `nix/packages/default.nix`: it currently has `dontBuild = true`,
   runs each command's checks and install target, and declares Python and
   brightnessctl for tam-monitor. Explicitly compile the native command,
   provide build inputs and preserve command discovery/endpoint contracts.
   Remove Python from this command's required runtime path when migrated;
   other commands can still use it. Keep optional brightness helpers scoped
   to their operation. Avoid unnecessary shell wrappers around the fast path.
3. Wire matching development packages into `flake.nix` and the developer
   module; cover both native-provided tools and the packaged-tool variant.
   Update consumer selection only through the recorded assembly mechanism.
4. If the proved access method needs a native helper or policy, include its
   immutable payload and exact native recipe/hash in the assembly. Otherwise
   retain the existing native payload with a verified unchanged-tree reason.
   Do not assume that an unprivileged C rewrite needs a new boot package.
5. After Fred supplies the tam pair, pin exact pushed source commits, refresh
   the lock, align source-derived versions and prepare the delivery record.
   Include tam command, corpus, library/API identities, built output paths,
   resource results and native payload decision. Keep earlier records intact.
